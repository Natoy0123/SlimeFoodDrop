 2. PART 1 - THE FONT SIZE QUESTION, ANSWERED WITH MEASUREMENTS
================================================================================
 The report is: "the font has been made bigger, but I am not satisfied, some
 parts still look small and some spacing is wrong or overlapping."

 That is exactly what the measurements predict. The type was raised in the
 builder, but the boxes the type lives in were not. Below is the trace, then the
 exact list of things that are broken right now.

------------------------------------------------------------------------------
 2.1 There is no single limiter; seven mechanisms stack
------------------------------------------------------------------------------
 The scene is rebuilt from code (Cause A), no text can wrap or shrink safely
 (Cause B), there is no layout system (Cause C), the geometry was hand-tuned
 around the previous sizes (Cause D), the canvas shrinks everything on small
 phones (Cause E), one of the two fonts is twice as wide as the other (Cause F),
 and the rects are shorter than the glyphs in several places (Cause G).

 Each is proven in the sections that follow. The important change since rev 1 is
 that Cause D is no longer "zero head-room somewhere" - the sizes have now been
 pushed past the geometry in five named places, which is why the screen looks
 worse in places even though the numbers went up.

------------------------------------------------------------------------------
 2.2 CAUSE A - your edits do not persist (proof)
------------------------------------------------------------------------------
 BuildMainGameScene.cs  BuildAll():
     EditorSceneManager.NewScene(NewSceneSetup.EmptyScene, NewSceneMode.Single)
 BuildAndroidApk.cs  BuildApk():
     BuildMainGameScene.BuildAll();   // before every build
 There are no prefabs, no scene overrides, no layout assets. Therefore:
   - Inspector edits are discarded on the next build
   - scene edits are discarded too (see 0.1: the scene is already one edit
     behind the builder)
   - the only durable type change is a change to BuildMainGameScene.cs
 This is why the project root carries 30 python scripts that rewrite C# by
 string replacement. They are a change log, not a build system.

 Practical rule: while the scene stays code-generated, change nothing in the
 Inspector that you are not also changing in the builder in the same sitting.

------------------------------------------------------------------------------
 2.3 CAUSE B - every label is created unable to wrap or shrink
------------------------------------------------------------------------------
 CreateUIText(...) in BuildMainGameScene.cs:
     txt.horizontalOverflow = HorizontalWrapMode.Overflow;
     txt.verticalOverflow   = VerticalWrapMode.Overflow;
     Shadow.effectDistance  = (3,-3)
     txt.raycastTarget      = false            <- good, keep
 Meaning, by default:
   - the text does not wrap; it paints outside its rect
   - overflow is visible, so growing type means overlapping the neighbour
   - there is no best-fit anywhere in the project (0 occurrences of
     resizeTextForBestFit / resizeTextMinSize / resizeTextMaxSize)
   - the 3 px shadow paints outside the box, so "fits" is 3 px optimistic
 61 of 151 labels opt into Wrap individually; 57 of those also set vertical
 Overflow = Truncate. That combination turns overflow into *silent clipping*
 rather than a visible overlap, which is why some text just loses its bottom.

 Measured glyph height (ascent + descent) versus the rects it is put in:
     22 px -> 26 px tall      24 px -> 29 px      26 px -> 31 px
     28 px -> 33 px           30 px -> 36 px      32 px -> 38 px
 Any rect shorter than that number clips the glyph, before line spacing.

------------------------------------------------------------------------------
 2.4 CAUSE C - there is no layout system
------------------------------------------------------------------------------
 Project-wide search in Assets/ for HorizontalLayoutGroup, VerticalLayoutGroup,
 GridLayoutGroup, ContentSizeFitter and LayoutElement returns ZERO results.
 Every panel is a fixed rect and every child sits at a hard-coded
 anchoredPosition. So:
   - a card cannot grow when its text grows
   - the width of one label is whatever is left over from its neighbours
   - the longest string of each label silently becomes the design constraint
 The visible symptom is what you described: some labels have big accidental gaps
 (their rect is wider than the string needs), others have none at all, and a few
 now collide (see 2.9).

------------------------------------------------------------------------------
 2.6 CAUSE E - the canvas scale still makes small phones unreadable
------------------------------------------------------------------------------
 CanvasScaler, BuildMainGameScene.cs:
     referenceResolution = 1080 x 1920
     screenMatchMode     = MatchWidthOrHeight
     matchWidthOrHeight  = 0.45

 Canvas scale factor (text paints at fontSize x factor):

   SCREEN         SCALE   22 px ->   25 px ->   28 px ->   32 px ->
   1080 x 1920    1.000     22.0      25.0       28.0       32.0
   1080 x 2340    1.093     24.0      27.3       30.6       35.0
   1080 x 2400    1.106     24.3      27.7       31.0       35.4
   1440 x 3200    1.474     32.4      36.9       41.3       47.2
    720 x 1600    0.737     16.2      18.4       20.6       23.6

 On a 720x1600 device a 25 px label paints at 18 physical px - about 1.6 mm.
 Mobile body text wants 2.5-3.5 mm. On 1080x2400 the new 28-32 px body text is
 fine (31-35 px); on 720p it is still caption-sized.
 Note also that matchWidthOrHeight 0.45 pinches the *logical* width on tall
 phones: on 1080x2400 the canvas is only 976 reference units wide, against a
 900 px tutorial card and a 940 px environment banner - i.e. the widest screens
 have about 18 px of slack per side. Do not raise this value to 1.0 to "get
 bigger text": that would shrink the logical width to 864 units and clip the
 dialogue cards. The safe fix is bigger type in the builder plus the container
 work, not a canvas trick. (See T6 for the large-text alternative.)

------------------------------------------------------------------------------
 2.7 CAUSE F - the two fonts have completely different widths
------------------------------------------------------------------------------
 PressStart2P is a 1-em-per-glyph arcade font; GameBody-Rounded is a normal
 proportional font. Same string, same size, measured:

   "BARRIER SHIELD  12.0s (1 HIT)"
        PressStart2P @23 = 667 px      Body @23 = 351 px
   "STAGE 7: STEAMWORKS SPIRE"
        PressStart2P @20 = 500 px      Body @20 = 308 px
   "! DANGER: 1 HEART LEFT !"
        PressStart2P @32 = 768 px      Body @32 = ~560 px

 So a label in PressStart2P hits its width limit at roughly half the font size
 of a body-font label. That is the "inconsistent optical weight" you are seeing:
 the HUD is body font at 25-32 px, the low-life banner and the power-up bars are
 arcade font at 23-32 px, and the almanac cards are arcade font at 20 px. Any
 label that must show a sentence should not be in PressStart2P.

------------------------------------------------------------------------------
 2.8 CAUSE G - the strings carry the layout work
------------------------------------------------------------------------------
 Double spaces are used as separators, and labels carry decorative prefixes and
 suffixes that consume the width the font size needs:

   "DIFFICULTY  <bullet>  MEDIUM MODE  (1/5)"     UIManager.cs 1085-1089
   "SLIME TUTOR  <bullet>  STEP 2/5"              UIManager.cs 1086-1089
   "MAGNET  6.0s" / "BARRIER SHIELD  12.0s (1 HIT)" / "TIME-SLOW  6.0s (50%)"
                                                  UIManager.cs 1752-1760
   "Lush Woodland Canopy  |  Peaceful Forest BGM" builder (EnvSubtitle)
   "Classic Arcade Pace  <bullet>  Balanced Drop Rates" builder (ModeDesc)
   "SCORE: " (7)  "BEST: " (6)  "STAGE: " (7)  "FRENZY: " (8)  "(1/5)"
 Measured cost:
   "STAGE: WHISPERING FOREST"  @25 = 377 px   ->  "WHISPERING FOREST" = 284 px
   "BARRIER SHIELD  12.0s (1 HIT)" @23 = 667  ->  "BARRIER 12.0s"      = 299 px
   "FRENZY: 15/15" @25 = 182                  ->  "15/15"              = ~90 px
 Removing the prefixes and the double spaces buys 50-370 px per label - in
 several cases more than a size bump would.

 Font coverage: GameBody-Rounded has 241 glyphs, Silkscreen 226, PressStart2P
 656. U+2022 (bullet) is present in the body font; U+00B7 (middot), U+2605
 (star) and U+2192 (arrow) are not. Stick to the bullet, never the other three.

 T1 - One source of truth for type (new file, 40 lines)
------------------------------------------------------------------------------
 Assets/Scripts/UiType.cs
     public static class UiType {
         public const float Scale = 1.00f;   // single global knob
         public const int Display = 40, H1 = 36, H2 = 32,
                          Body = 28, Label = 26, Caption = 24, Micro = 22;

------------------------------------------------------------------------------
 T6 - Canvas decision (do not use it as a shortcut)
------------------------------------------------------------------------------
 Keep 1080x1920 / match 0.45. Raising match to 1.0 gives +13% text on a 720x1600
 device (0.737 -> 0.833) but shrinks the logical width to 864 units, which clips
 the 900 px tutorial card and the 940 px environment banner. Not worth it.
 The honest lever for small phones is a player-facing one:
     Settings > "LARGE TEXT"  ->  UiType.Scale = 1.20
 which, combined with T1 and with best-fit on HUD labels (T7), grows every
 string without editing 151 rects. Ship the toggle with the type system, not
 before it.

------------------------------------------------------------------------------
 T7 - Text policy instead of defaults
------------------------------------------------------------------------------
   HudLabel   horizontal Overflow, bestFit ON, max = token, min = Caption
              (grows to the design size, shrinks only for a 6-digit score or a
               translated string)

 5. PART 4 - ART DIRECTION (numbers re-measured)
==============================================================================
 5.1 The conflict
   Slime            758x466, 42 frames, bilinear, soft AA cartoon
   Food / hazard    18x18 exactly (22 food + 4 hazard), point, 30 PPU
   Backgrounds      17 layers at 272x384, 10 at 320x180, 8 at 384x384,
                    8 at 640x384, 4 at 683x384, 3 at 544x384, 1 at 213x384
   UI icons         32x32 x13, 24x24 x1, 48x64, 64x64, 96x128 x2, one 924x483
   Type             GameBody-Rounded (smooth) + PressStart2P (pixel)
   One gameplay frame mixes a bilinear blob with 18 px point-filtered food under
   a pixel logo with rounded-vector type. Each piece is fine alone; together
   they read as an asset mashup.

 5.2 Pick one direction
   (a) Pixel: re-render the slime and splash art on a native grid (64-96 px
       body), point filter, integer scale, pixel font only. Cheapest, most
       coherent, matches 39 background layers and the logo.
   (b) Smooth: redraw the 26 item sprites at 64-128 px, bilinear everywhere,
       body font only, keep the slime and the splash cutscene.
   Recommendation: (a) - the 51 background files are already pixel art and cover
   most of the screen; the item set is 26 small sprites against 42 slime frames
   plus 14 splash images.

 5.3 Pixel scaling is fractional
   ResponsiveCamera.ScaleAndPositionRenderer computes
       requiredWidth = visibleW * 1.14   (14% parallax bleed)
       uniformScale = max(requiredWidth / sprite.bounds.x, ...)
   On a 1080-wide device a 272 px background is stretched to 1231 px = 4.53x,
   then shifted for parallax every frame. Fractional point scaling is what makes
   edges crawl while the slime moves. Fix: round to an integer multiple (4x),
   derive the camera size from it, or use Bilinear and accept softness.

 5.4 UI icon grid is mixed
   32 px, 24 px, 64 px and 96x128 in the same HUD family. Pick 32 px and
   regenerate the odd ones, or accept a 1 px outline pass to unify.

 6. PART 5 - SIZE AND PERFORMANCE (weights measured on disk)
==============================================================================
 6.1 Textures
   All 225 sprite PNGs are imported Uncompressed (PixelArtImportSetup.cs 14).
   Raw RGBA in VRAM: 178.4 MB. The slime alone is 42 x 758x466 x 4 = 59.3 MB,
   and the body fills ~344 of the 758 px width, so most of that is transparent
   padding. Fix in order: atlas the 5 slime animations and tight-pack, then ASTC
   6x6 or 8x8. Target: slime under 8 MB resident, all sprites under 40 MB.

 6.2 Build weight
   APK: 45,507,060 bytes (45.5 MB). Audio: 36 MB of it, dominated by
   BGM_Industrial_ChiptuneFactory 15.01 MB, BGM_Night_ColdNight 8.37 MB,
   BGM_Underwater_OceanWave 6.81 MB. These are loops: re-encode at 96-128 kbps
   Ogg (a 2-minute loop at 128 kbps is 1.9 MB). Also delete
   Assets/Sprites/Background_Backup (1.7 MB, ships and doubles import time).
   Target: soundtrack under 8 MB, APK under 18 MB - the cheapest install-rate win
   available.

 6.3 PlayerPrefs.Save() in the scoring path
   GameManager.AddScore writes SetInt + Save() every time the score passes the
   best, i.e. on every catch for the rest of a record run. On Android that is a
   synchronous disk write inside gameplay. Keep the value in memory, write once
   in TriggerGameOver() and OnApplicationPause(true).

 6.4 No pooling
   ItemSpawner instantiates a falling item and FallingItem destroys itself on
   catch; UIManager.SpawnFloatingStreakIndicator / SpawnFloatingRushBonus /
   SpawnStreakBrokenIndicator each build a new GameObject + Text + Outline +
   CanvasGroup and animate it. At a 0.36 s spawn interval that is steady GC
   churn. Pool 24 items and 6 floating labels.

 6.5 Frame rate and focus
   No Application.targetFrameRate, no Screen.sleepTimeout, no
   OnApplicationPause/Focus anywhere in Assets/. Set 60 fps, keep the screen
   awake in a run, pause and save on focus loss.

 6.6 Physics mix
   FallingItem requires a Rigidbody2D, sets it Dynamic with gravityScale 0, then
   moves it by writing transform.position, and detects catches three ways
   (manual distance in Update, OnTriggerEnter2D, OnTriggerStay2D + a guard
   flag). Make it kinematic or non-physics and keep one catch path.

 7. PART 6 - DESIGN AND PROGRESSION
==============================================================================
 7.1 No meta-progression
   ThemeManager.InitializeStartingTheme sets currentThemeIndex = 0 on every run.
   Ten hand-built biomes - the largest production investment in the game - are
   discarded each time, and only a high score persists. Persist "biomes
   discovered" and show them as a collection row in the existing Almanac.

 7.2 Biome pacing is front-loaded
   Unlock scores are 0, 100, 250, 450, 700, 1000, 1350, 1750, 2200, 2700: six
   biomes and six music tracks in the first two minutes, then a long tail. Most
   players never hear the 15 MB industrial track. Either compress the tail or
   slow the head so each biome holds the screen for 30-45 s.

 7.3 Food Rush dominates scoring
   Rush drops the spawn interval to 0.36 s, removes poison, adds +10 base and
   keeps the combo. One 15 s rush can dwarf the previous two minutes. Cap the
   per-item bonus during a rush, or make the rush double the combo instead.

 7.4 Power-up competition
   Four power-ups compete from one spawn pool via additive thresholds in
   ItemSpawner.ChooseItemType. Hearts strictly dominate shields on Easy, and
   Magnet never pulls hearts. Replace the additive chain with one weighted table
   with comments on intent.

 Method: parsed the built scene for all 401 RectTransforms (anchors, pivots,
 sizeDelta, parent chain), re-solved the entire UI tree at 17 real device
